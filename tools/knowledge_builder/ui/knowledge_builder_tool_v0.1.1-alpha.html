Knowledge Data Builder — α0.1.1（早期評価用ビルド）

Knowledge Data Contract 0.1 準拠 / 今回の改善テーマ: 件数が増えても全件を人が確認しなくてよいUIへ（詳細は同梱README参照）

これは限定評価用の動作物です。正式な設計判断・成果物提出には使用しないでください。 評価目的: 画面の分かりやすさ・必要なNodeへ絞り込めるか・複数Nodeの一括操作・未処理の関連候補への絞り込み・ 複数候補の一括採用/却下・Knowledge Graphでの「文書内階層」と「文書間関連」の区別・Knowledge JSON保存までの一連操作。

1. データを読み込む (既存Trace JSON)

既存のPDF/Excelツールが出力した「照合用JSON（trace JSON）」を読み込みます。PDF/Excelファイルそのものは読み込めません。 先に既存ツールでtrace JSONを出力してから、ここへ読み込ませてください。

2. ノードを確認・修正 (Knowledge Nodes)

文書から生成された"知識の単位"（ノード / Knowledge Node）を確認します。通常は全件を修正する必要はありません。 内容・種別・タグに誤りがある項目だけ修正してください。件数が多い場合は下の検索・絞り込みを使ってください。
選択中: 0件
表示中: 0件 / 全0件
状態文書種別タイトル本文タグ信頼度出典

3. 文書間の関連を確認 (Relations / Edges)

文書Aと文書Bのノードから、"関連している可能性がある組み合わせ"を自動抽出します。候補を確認し、 正しければ「採用」、誤っていれば「却下」してください。採用した関係がKnowledge Graph上のEdge（つながり）になります。 現時点はタグの一致・文字列の似ている度合いだけで候補を出しているため、「関連がありそう」までしか判定していません （「要求を満足している」の判定はまだ行っていません）。

表示中: 0件
状態関係要求Node(A)設計Node(B)信頼度根拠(evidence)操作

4. ナレッジグラフを確認 (Knowledge Graph)

ノード同士のつながりを図で確認します。「文書間の関連」（文書Aと文書Bをつなぐ線）と、 「文書内の階層関係」（章 → 節 → 項目など、元文書内の親子関係）を色分けして区別しています。 まず確認したいのは通常「文書間の関連」なので、「文書内の階層関係」は初期状態では非表示にしています。

5. ナレッジデータを保存

作業量サマリ（件数が増えても人の操作件数を減らせているかの目安。α0.1.1で追加）。 「操作対象にしたNode数」は選択または修正したNodeの重複除外件数であり、内容を実際に確認したことの保証ではありません。
